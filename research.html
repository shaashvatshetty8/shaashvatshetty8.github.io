Profiling and pruning visual-token KV caches in Qwen2.5-VL

Does Mustafar-style unstructured magnitude pruning, developed for text-only caches, transfer to visual tokens? Advised by Prof. Bahar Asgari. Continuing as an independent study.

The problem

A vision-language model reads an image by turning it into tokens — hundreds of them for a photo, more than a thousand for a single page of a document. Each one adds a Key and a Value entry to the cache at every transformer layer, and those entries sit in GPU memory for the whole generation. Past a certain size the KV cache, not the model's weights, is what you are actually paying to serve.

Recent work shrinks the KV cache of text-only models by exploiting structure inside it: a handful of large-magnitude elements and outlier channels carry most of the signal, so the rest can go. Mustafar turns that into one rule — per-token magnitude pruning at the element level. But that structure had only ever been measured in text caches. Nobody had checked whether a visual token's Key vector, which comes out of a vision encoder rather than a language model, looks the same. If it does, the rule transfers for free. If it does not, applying it anyway quietly discards visual information the model needs.

So this project measures first and prunes second. Profiling answers the structural question; the pruning study is the validation step, not the assumed conclusion.

Method

How it was built

01 — Capture & profile

Prefill Key and Value tensors are saved per layer and split into visual and text positions. Qwen2.5-VL marks image placeholder tokens explicitly, so the split is verifiable rather than guessed. Magnitude distributions, channel concentration and visual-to-text ratios are profiled on calibration sets of up to 500 images from COCO, ImageNet and TextVQA.

02 — Prune during generation

Mustafar's token-wise magnitude rule is applied during real generation, not scored offline, and only to visual-token entries. Text entries stay dense throughout, so any accuracy change is attributable to visual pruning alone. Every compared run is pixel-matched to a fixed visual-token budget, checked per example with zero mismatches.

03 — Store it for real

A pruned tensor is cut into 64-element tiles. Each tile holds its surviving values packed tightly, a 64-bit bitmap marking which positions survived, and a 32-bit offset into the packed array. The cache reports its actual byte count while generating, so memory numbers are measured rather than calculated.

The three controls

Three controls isolate what actually drives the accuracy change, rather than letting one explanation go unchallenged:

  • Random — the same achieved sparsity, with entries chosen at random instead of by magnitude.
  • Uniform — the magnitude rule applied to text Keys as well as visual Keys.
  • Structured — whole channels dropped by the same magnitude score, at matched sparsity.
Results

What the measurements say

Accuracy uses fixed-reference, right-or-wrong metrics rather than text-similarity scores: relaxed VQA accuracy on TextVQA, ANLS on DocVQA, 500 examples each.

Finding 1. Visual-token Key caches carry the same layer-wise outlier-channel concentration as text-token Key caches, at comparable magnitude. Across all 36 layers both curves rise and fall together, including a shared spike near layer 27 where both jump from about 0.15 to over 0.30. Mean absolute Key magnitude stays within roughly a factor of two between modalities almost everywhere. There is no separate "visual regime" for Mustafar's rule to miss.

Magnitude pruning holds to 90% sparsity. Random collapses immediately.

Two things follow. Selecting by magnitude is what matters — the random control's immediate collapse shows the visual Key cache really does contain exploitable structure, and Mustafar's rule finds it. And the modality difference is narrower than "visual tokens are special": text Keys are also safely prunable to 70%. The danger zone is 80–90% sparsity in general, not text tokens in particular.

Finding 2. Pruning Keys or Values alone is safe to 90% sparsity on both datasets. Pruning both together is safe only to 70%, and past that fails harder than either alone — at 90% the Key-only and Value-only arms beat the combined arm by 0.15–0.25 accuracy points, with 95% confidence intervals that exclude zero on both datasets.

Measured savings land within one to two percentage points of the calculated ones, on both datasets and both storage paths. The measured number is slightly smaller because the real format pays costs the arithmetic treats ideally: per-tile bitmaps and offsets, and nonzero counts padded to multiples of eight so reads stay aligned. That agreement is the point. The memory claim rests on a format that actually runs, not on a formula.

The negative result

The kernel is correct, and slower than dense

The bitmap format only pays off if attention never has to decompress it. Mustafar's CUDA kernel computes straight from the packed tiles. It works. It just isn't faster here.

RTX A4000, Qwen2.5-VL's 16-query / 2-KV-head geometry, Key 70% / Value 80%. Lower is better.

Dense (PyTorch Flash-Decoding) Mustafar Key + Value kernels only Whole Mustafar arm, including glue

The comparison is fair: profiling confirmed the dense baseline dispatches to flash_fwd_splitkv_kernel, PyTorch's bundled FlashAttention-2 decode path — the same class of kernel Mustafar's own paper compares against.

Correctness is not the issue. Integrated through its upstream reference calling convention and compared against the dense-zero path, the kernel produced zero prediction mismatches across 500 examples on both TextVQA and DocVQA. Speed is the issue, and it has two separate causes.

GPU time. Mustafar's kernel is 5–7× slower than Flash-Decoding at this model's 16-query / 2-KV-head geometry even before counting integration overhead, likely because per-query-head batching re-reads each compressed KV head eight times and leaves most tensor-core rows idle.

Launch overhead. On top of that, the path issues about 15 separate CPU-side kernel launches per attention call against dense's two. Wall time sits flat near 405 µs across batch sizes 1 to 8 while GPU work triples underneath. Fusing that glue would bring wall time down toward the GPU-time floor — but that floor is still several times slower than dense, so fusion alone will not close the gap.

There is also a more basic question to settle before more kernel tuning. At batch 1 this model's dense KV cache is only about 1 MB per layer, small enough that it may never leave the GPU's L2 cache. Mustafar's whole performance case assumes decoding is limited by DRAM bandwidth. If the working set stays resident in L2 at this context length, that assumption is not actually being tested, and the comparison would need to move to longer contexts or larger batches to be a fair test of the kernel's design point.

One separate finding concerns the compression step itself. The Triton converters that pack the cache into bitmap form are cheap once amortised — 0.04–0.17% of a decode step, spread over 1,024 generated tokens. But they issue 10 to 66 device-to-host memory copies per call. Those round-trips through the CPU are a plausible mechanism for the time-to-first-token increase Mustafar's own paper reports, independent of anything in this integration.

Implications

What this is good for

Practical

A serving system can cut stored KV-cache memory roughly in half at under a two-point accuracy cost, pruning visual-token entries almost exclusively. Because this works inside each token's cache vector rather than removing whole tokens, it composes with token-dropping and quantisation instead of competing with them.

Scientific

Text-only KV-cache compression assumptions do transfer to visual tokens in this model. The same magnitude structure is there and the same rule exploits it the same way. What remains is a difference in sparsity tolerance at the extreme end, not a difference in which rule applies.

Systems

The memory win is real, and the measured-versus-calculated agreement shows the bitmap format delivers what its arithmetic promises. The speed win depends heavily on attention-head geometry and kernel engineering, and it did not materialise against a modern FlashAttention baseline.

Limitations, stated up front

One model (Qwen2.5-VL-3B). Accuracy scored on the dense-zero path, where pruned entries are zeroed rather than physically removed. The first generated token always comes from dense prefill, and VQA answers are short, so the decode-time test of pruning is conservative.

Ongoing

Where it goes next

The project continues as an independent study with the supervising professor through the school year, along two tracks.

Importance-aware, per-token pruning

Right now every visual token gets the same sparsity target, and the random control suggests that leaves something on the table: the cache's usable structure is spread unevenly across tokens. A question about text in a document's corner makes most of the page's white space irrelevant. The current work tests whether per-token importance can be estimated cheaply enough at inference time to set a non-uniform budget — prune an unimportant patch at 90% while an important one stays near 70% — and whether that beats the fixed-sparsity curve at the same average memory budget.

Closing the kernel speed gap

Getting a real end-to-end, batched model.generate timing rather than per-layer numbers is the next concrete step, and it requires extending the kernel's decode path past its current batch-1 limit. Before more tuning, the L2-residency question above has to be settled, or the benchmark is not testing what it claims to test.
