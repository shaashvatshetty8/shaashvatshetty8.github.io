HeyDoug — a multilingual AI debugging tutor

Hold down a physical button wired to a Raspberry Pi, describe your bug out loud in English or Spanish, and Doug highlights the offending line directly in your VS Code editor while speaking the explanation back to you in the language you asked in.

The premise came from what existing assistants optimise for. Copilot and Cursor are built to output code, which is a different goal from building a student's understanding. The gap we aimed at was students who do not speak English as a first language and cannot afford tutoring.

How a question travels

1 · Press and speak

A GPIO button starts a PulseAudio capture from a Bluetooth mic at 16 kHz. A second physical switch selects English or Spanish.

2 · Transcribe and queue

Release uploads the clip to ElevenLabs speech-to-text. The transcript becomes a job document in MongoDB Atlas, which decouples the hardware from the editor entirely.

3 · Read the codebase

The extension polls that queue, translates Spanish to English through DeepL when needed, and sends the question plus up to 25 workspace files to Gemini.

4 · Highlight and speak

Gemini returns structured JSON naming the file, line and explanation. The extension highlights that line, dims the rest, renders the answer in a sidebar, and sends it back out as speech in the original language.

What I'd point at

Using a database as the message bus between a Pi and a VS Code extension meant neither side had to know the other existed, or share a network. It is not elegant, but at a hackathon it turned an integration problem into two independent ones.

Robustness details

A 30-second hard timeout per model call, retry on rate-limit responses with a live "retrying, 1 of 3" status in the footer, and a greeting fast-path that skips gathering the codebase when someone just says hello.

Beyond one bug

Multi-bug and multi-file highlighting, per-bug fix / skip / ignore-all controls, and a chat panel that carries the last five exchanges into the next prompt so follow-up questions work.

Personal project

A chatbot fine-tuned to text like me

Turning a personal message archive into a training set, fine-tuning a small Llama on it, and serving the result locally.

On the data. The training set is private correspondence between real people, so it is not published here, not committed to any repository, and never leaves the machine it was built on. The exports, the parsed conversations, the JSONL splits and the trained adapter all stay local. What is described below is the method, not the data.

The idea is simple enough to state and fiddly to execute: a model that replies the way I actually text, lowercase and short, rather than the way an assistant thinks a person texts. The interesting work is almost entirely in the dataset, not the training.

The pipeline

  • Export. A shell step dumps the local message database to one plain-text file per conversation. It needs full-disk access, which is itself a useful reminder of how sensitive the input is.
  • Parse. A regex block parser pulls timestamp, sender and body out of each export, then strips the noise that would otherwise be learned as style: tapback reactions, attachment placeholders, link unfurls and leaked file paths. Consecutive messages from the same person get merged into a single turn, because that is what a turn actually is.
  • Build the dataset. A sliding window of the three previous turns becomes the user message, and my own reply becomes the assistant message, under a fixed system prompt describing the voice. Replies over 200 characters are dropped as unrepresentative. The result is roughly 3,000 instruction pairs in chat-format JSONL, split 90/10 into train and validation.
  • Fine-tune. 4-bit QLoRA on Llama-3.2-3B-Instruct through Unsloth and PEFT, LoRA rank 16, targeting the attention and MLP projections, trained with TRL's supervised trainer for two epochs on a cosine schedule at a 512-token context. The best validation-loss checkpoint wins. An alternate path uploads the same JSONL to a hosted fine-tuning API for comparison.
  • Serve. A FastAPI server loads the base model in half precision and applies the LoRA adapter on top, selecting Apple Silicon, CUDA or CPU automatically. A single POST endpoint takes a message plus history and returns a reply, sampled short and warm to match the register.
  • Interface. One HTML file, no framework and no dependencies, styled as a phone messaging app with a status bar, bubbles, a live clock and animated typing dots. It rebuilds the last three turns into exactly the format used during training, which matters more than it sounds like it should.

What I learned

Two things. First, the gap between "the model saw this format" and "the model sees this format at inference" is where personality models quietly fail — the UI has to reconstruct the prompt the same way the dataset did, or the fine-tune appears not to have worked. Second, most of the quality came from cleaning decisions that look trivial written down. Merging consecutive messages and dropping long replies changed the output register far more than any hyperparameter did.

Research engineering

A bitmap-compressed KV cache that reports its own size

The systems half of the DREU research project, treated as an artefact rather than a result.

Unstructured sparsity is normally hard to use on a GPU. The surviving values sit at irregular positions, and finding them can cost more than the skipped work saves. The answer, borrowed from Coruscant and Mustafar, is a bitmap format: cut the tensor into 64-element tiles, keep each tile's nonzero values packed tightly together, and store one bit per element marking which positions survived plus a 32-bit offset into the packed array. Nonzero counts are padded to multiples of eight so memory reads stay aligned.

The part I care about is the verification. A CPU test suite proves the compressed path produces bit-identical output to the dense path, and a full parity run on real examples returned identical predictions. The cache then reports its actual byte count during generation, so the memory numbers in the write-up are measured rather than derived — and they land within one to two percentage points of what the analytic model predicts.

Seven classifiers, one dataset, one honest comparison

A benchmark of seven models on Fashion-MNIST, from classical algorithms like support vector machines through to a convolutional network built for the task. The point was not to find the winner — everyone knows the CNN wins — but to quantify what you give up by not using one, and what it costs you to use one.

  • PCA for dimensionality reduction, with the retained-variance choice justified rather than assumed.
  • Five-fold cross-validation on every model, so the ranking is not an artefact of one split.
  • Confusion matrices to see which garments each model confuses, which is where the classical models differ most interestingly from each other.
  • An engineered CNN reaching 91.05% accuracy, against the traditional baselines.
  • A trade-off analysis pairing accuracy gained against training cost paid.

Which map-matching algorithm survives a bad GPS fix?

Map matching is the problem of deciding which road a noisy GPS trace was actually on. I implemented four algorithms from scratch and designed a test harness that puts each of them in the conditions it is supposed to handle well and the conditions it is not.

  • Synthetic trajectories generated with controlled noise, so error magnitude is an independent variable rather than whatever the recorder happened to produce.
  • Dense urban road networks, where candidate roads are close together and the decision is hard, against sparse rural ones, where the failure mode is different.
  • The same metrics across all four, so the comparison means something.

UCSC Science Internship Program · Summer 2022

Telling a drone what to look for, in plain English

An object detector knows a fixed list of labels. A person giving an instruction does not. This project bridged that gap so a drone could take a natural-language command, work out what object it referred to, and go find it visually.

  • Benchmarked YOLOv5 against YOLOv3 and chose YOLOv3 for roughly 35% faster inference on the constrained onboard hardware — the newer model was not the right model for the constraint.
  • Matched the command's target word to the detector's label set with cosine similarity over word embeddings, which absorbs synonym variation without retraining anything.
  • Wired detection and matching together into a navigation loop that tracks the identified object.
